# Pinned FSRS scheduling spike (T-002 / W02)

Verified with **ts-fsrs 5.4.2**, whose `FSRSVersion` is **v5.4.2 using FSRS-6.0**, on
Node 24.21.0. `package.json` pins the exact runtime version and `package-lock.json` pins its
integrity. The package is MIT licensed, has no runtime dependencies and requires Node >=20.
The npm package is 706,415 bytes unpacked; its ESM distribution is 61,245 bytes before compression
(including comments). This spike does not import it into the application bundle.

This records library behavior for blueprint sections 5 (A05/A06), 11.1 and 25. It supplies native
fixtures for W10; it does not implement the adapter, persistence, replay, eligibility or grading
policy. T02 and T18 test titles cover only preview agreement and serialization prerequisites;
the full application cases remain W10's responsibility.

## Reproducing the fixtures

The committed [scheduling.json](../../../src/infrastructure/fsrs/fixtures/scheduling.json) was
generated by calling the installed library, not by transcribing expected calculations.
[spike-inputs.ts](../../../src/infrastructure/fsrs/spike-inputs.ts) holds all fixed instants and
ratings. From the repository root:

```sh
npm ci
node src/infrastructure/fsrs/generate-fixtures.ts
npx prettier --write src/infrastructure/fsrs/fixtures/scheduling.json
npx vitest run src/infrastructure/fsrs/fsrs.test.ts
git diff -- src/infrastructure/fsrs/fixtures/scheduling.json
```

Regeneration is an explicit review operation, never part of the test run. With this version and
inputs, it must produce no fixture diff. Compare any upgrade against the old fixtures before
accepting changed outcomes. Tests compare full native cards and logs, without rounding floating
point values, using ISO UTC dates and state/rating names for readability.

The starting configuration is exactly:

```json
{
  "request_retention": 0.9,
  "maximum_interval": 365,
  "enable_short_term": true,
  "enable_fuzz": false,
  "learning_steps": ["1m", "10m"],
  "relearning_steps": ["1m", "10m"]
}
```

`fsrs(config).parameters` resolves the library's 21 FSRS-6 weights. The fixture records that full
resolved parameter set and checks it alongside the engine version. Explicit relearning steps
matter: the package default is only `["10m"]`.

## API and preview versus commit

- `createEmptyCard(fixedDate)` returns a New card with zero counters and memory values, no
  `last_review`, and `due` equal to the supplied instant.
- `fsrs(config)` constructs the scheduler; `parameters` exposes the resolved configuration.
- `repeat(card, evaluationDate)` previews all four ratings, indexed by `Rating.Again` (1),
  `Hard` (2), `Good` (3) and `Easy` (4).
- `next(card, evaluationDate, rating)` produces one `{ card, log }` transition. Rating.Manual (0)
  is not an ordinary grade. There is no separate persistence or commit API: the caller chooses
  the resulting card to save.

For identical inputs, every preview card **and log** equals the `next` result. The fixtures cover
New, both Learning steps, Review after several reviews, both Relearning steps, and a mature Review
at the interval limit, for all four ratings. Neither API mutates the supplied card or evaluation
instant. Repeated calls on the same scheduler and a fresh scheduler agree with fuzz off. These
properties do not authorize reusing a stale preview: W10 must use the actual final evaluation time
and current state.

## State fields

| Native card field | Observed meaning |
| --- | --- |
| `state` | Enum: New=0, Learning=1, Review=2, Relearning=3; JSON fixtures display names |
| `due` | Raw proposed due `Date`, independent of application study-day eligibility |
| `last_review` | Evaluation instant of the latest rating; absent on a fresh New card |
| `stability` | Memory estimate in days, representing the interval at 90% retrievability; not the rounded scheduled interval |
| `difficulty` | Memory difficulty estimate; initialized by the first grade and updated thereafter |
| `learning_steps` | Zero-based step index, not an array or count of repetitions; resets to 0 on graduation |
| `scheduled_days` | Integer scheduled interval in days; 0 for the intraday steps used here |
| `elapsed_days` | Elapsed days used in the latest transition; deprecated by the vendor for v6 |
| `reps` | Number of ratings, including Learning/Relearning ratings |
| `lapses` | Increments when Review/Again enters Relearning; another Again in Relearning does not increment it |

The review log describes the **input** memory values, state, step and scheduled interval,
with `rating` and `review` identifying the transition. Its `due` is the previous `last_review`
(or the initial due on a New card), not the newly proposed due. `elapsed_days` is this transition's
elapsed interval and `last_elapsed_days` is the preceding card's value; both log fields are
deprecated for v6. Preserve the complete log if retaining native history; do not interpret it as
the updated card.

## Step and interval semantics

New card evaluated at `2026-01-01T12:00:00.000Z`:

| Rating | Result state | Step | Due (UTC) | Scheduled days | Stability | Difficulty |
| --- | --- | --- | --- | --- | --- | --- |
| Again | Learning | 0 | 2026-01-01T12:01:00.000Z | 0 | 0.212 | 6.4133 |
| Hard | Learning | 0 | 2026-01-01T12:06:00.000Z | 0 | 1.2931 | 5.11217071 |
| Good | Learning | 1 | 2026-01-01T12:10:00.000Z | 0 | 2.3065 | 2.11810397 |
| Easy | Review | 0 | 2026-01-09T12:00:00.000Z | 8 | 8.2956 | 1 |

For Learning and Relearning with these steps:

- Again resets to step 0 and schedules one minute.
- Hard retains the current step and schedules **six minutes at either step**, the rounded
  average of 1m and 10m. In particular, step-1 Hard is not a ten-minute delay in this version.
- Good advances from step 0 to step 1 with ten minutes; from step 1 it graduates to Review.
- Easy skips the remaining steps and enters Review with a memory-derived day interval.

The sequential `learning-reviews-lapse-relearning` fixture proves:

1. Good at creation enters Learning step 1. Good at 12:10 graduates with two scheduled days,
   due `2026-01-03T12:10:00.000Z`.
2. Good, Hard and Easy at the successive due instants schedule 11, 32 and 146 days.
3. Again at `2026-07-11T12:10:00.000Z` enters Relearning step 0, increases lapses to 1, and is
   due at 12:11. Good then moves to step 1, due at 12:21. Good at 12:21 returns to Review with
   four scheduled days, due `2026-07-15T12:21:00.000Z`.

**Units and maximum edge:** `maximum_interval` is in days, as is `scheduled_days`. Native due
calculation adds elapsed multiples of 24 hours for day intervals, or 60 seconds for minute steps.
It does not perform zoned calendar arithmetic; application study-day projection belongs to W10's
time-policy boundary. Intraday `scheduled_days: 0` still has a real future due instant.

The vendor's `next_interval` rounds and clamps to `[1, maximum_interval]`, but the Review scheduler
then forces `Good >= Hard + 1` and `Easy >= Good + 1` without another clamp. The
`easy-reviews-reach-maximum` trace reaches 365 days after three Easy ratings. At its next due
instant, `2027-03-16T12:00:00.000Z`, the `review-at-maximum` matrix records **Hard=365,
Good=366, Easy=367 days**, despite `maximum_interval: 365`. The fixture and a dedicated test lock
down this finding rather than asserting a cap the package does not enforce. No app policy or
vendor patch is added in this spike.

## Serialization

`JSON.stringify(card)` serializes `due` and `last_review` as ISO strings and keeps the numeric
state and memory fields. `JSON.parse` leaves those timestamps as strings. `TypeConvert.card`
restores them to `Date` instances (and accepts numeric or named states); `CardInput` also accepts
date strings directly. `TypeConvert.review_log` performs equivalent log conversions.

The JSON round-trip test first produces a card through five actual ratings, serializes and parses
it, restores it with `TypeConvert.card`, checks all fields, then compares the next native card and
log for every grade at the same fixed instant. Conversion is not schema validation: numeric
state/rating values and arbitrary fields are not comprehensively validated. W10 must validate
external snapshots before conversion and version the serialized format. The fixture generator's
state/rating names are a readability convention, not a production backup contract.

## Open questions for W10

- How will the adapter honor the product's 365-day limit when this version returns 366/367?
  Decide between a reviewed upstream fix/version and an explicit, versioned interval policy;
  keep native proposals observable and apply any chosen policy equally to preview, rating and replay.
- Define the snapshot schema, validation and serialization version, including absent
  `last_review` for New cards and compatibility with the vendor's planned removal of deprecated
  fields in v6.
- Store exact package/engine versions, resolved weights, parameter-set identity and policy version
  with transitions; define unsupported-version handling and an upgrade/replay/rollback strategy.
- Preserve native due and integer scheduled days while projecting study-day eligibility in the
  time adapter. Refresh previews after state/time changes and capture grading time once.
- Verify history utilities, undo and replay against retained transitions; this spike only tests
  single transitions and JSON continuation, not persistence or replay.
